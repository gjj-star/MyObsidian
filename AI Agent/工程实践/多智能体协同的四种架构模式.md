# 多智能体协同的四种架构模式

**英文**：Multi-Agent Orchestration Patterns（多智能体协同架构模式）；Agent（智能体）；Tools in a Loop（工具循环）；Orchestrator-Workers（编排者-工作者）；State Machine（状态机）

判断一个系统是不是多 Agent 架构，关键不是看有几个模型、几个节点，而是看：节点有没有**独立职责**、能不能做局部决策并调用工具、节点之间有没有**真正的协作关系**。

## 三级演进：从单 Agent 到协同系统

| 级别 | 形态 | 特征与边界 |
|---|---|---|
| 第一级 | 单 Agent + 工具 | 所有判断在一个上下文里完成，无交接问题；天花板：上下文被撑爆、只能串行、塞得越满注意力越差 |
| 第二级 | 子任务外包 | 主 Agent 把只读的脏活（查资料/搜代码/读文档）外包给临时子 Agent，只回传**压缩后的结论**而非原始材料；市面上大部分号称"多 Agent"的系统只到这一级，已能满足多数场景 |
| 第三级 | 真正的多 Agent 协同 | 每个 Agent 有自己的上下文、职责、工具和状态，中间必须有**显式编排层**（谁派活、谁能动系统、谁判断完成）；代价是 token 消耗达单 Agent 十几倍，线上故障大多发生在 Agent 与 Agent 之间而非内部 |

## 四种架构模式

![[Multi-Agent的四种架构模式.png]]

1. **编排者-工作者**：一个大脑派活，多双手干活。生产环境最成熟，Deep Research 类产品底层都是它。设计要点：子 Agent 只读、回传的是结论与证据而非原始材料、最终拍板必须回到主 Agent（否则各说各话）。适合广度优先的任务：深度调研、竞品分析、大代码库只读检索
2. **顺序流水线**：一个 Agent 处理完交给下一个，按步骤推进（需求分析 → 方案设计 → 实现 → 审查）。关键不在每一步多强，而在**交接是否清楚**：目标、约束、风险缺一项，方向就偏了且系统不报错
3. **群体讨论**：多个角色 Agent 共享一个对话线程，各自代表一个视角。价值是补充视角而非提高效率，适合方案评审、风险检查；不稳定（重复讨论、议题跑偏），真实系统要配**主持人**限制轮次、控制议题、最后总结
4. **图状态机**：把协作画成显式流程图，Agent 是节点、流转是边，状态集中管理，关键步骤可插人工审批。牺牲灵活性（路径要提前设计）换来治理能力：每步可回放、可打断、可审计，适合高风险操作、合规流程

## 选型与设计原则

- **选型一句话**：能分头查的（只读、依赖少）→ 编排者；有工序的 → 流水线；要碰撞的 → 圆桌（配主持人）；要治理的 → 状态机。需要一起改的（写操作多、依赖强）要非常谨慎
- **写操作尽量单线程**：多个 Agent 同时改同一份代码/同一个系统必然互相踩踏；多出来的 Agent 更适合提供判断和建议，不适合同时抢执行权
- **问题多出在设计上**：分析上千条真实执行轨迹，很多失败源于任务描述不清、协作关系没设计好——换更强的模型救不了糟糕的协同设计
- **成本要在架构阶段设计**：每个 Agent 都是一次独立推理，Agent 间传递信息也消耗 token；多 Agent 本质是用更多算力换处理能力，值不值取决于任务价值
- **通信协议仍是半开放问题**：Agent 间通信协议层还在标准化过程中——未来多 Agent 架构的竞争力在**通信与治理层面**，而不是单个 Agent 有多聪明
